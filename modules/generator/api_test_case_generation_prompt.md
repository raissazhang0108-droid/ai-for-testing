## 1. 交付格式与结构规范
* **单 Sheet 聚合**：所有生成的测试用例必须合并输出到同一个表格（Excel 格式 / Markdown 表格）中，表头统一使用中文。
* **命名规范**：
  * **用例名称**：清晰描述测试意图（如：`【P0】创建订单-正向核心场景`）。
  * **文件名称**：根据接口功能生成符合代码/文件命名风格的英文名称（如：`create_order_success.json`）。
* **上下文动态关联**：若请求参数需要从前置条件（如上游接口返回值）中动态获取，必须使用 `{{参数名}}` 占位符进行标注。

## 2. 优先级定级严格规则
在所有文档/表格的标题前，必须显式展示优先级前缀（格式如：`1. 【P0】用例标题`）。定级标准严格如下：
* **【P0】核心正向场景**：接口的核心业务 Happy Path、主流程。
* **【P1】边界正向场景**：参数处于合法临界值、可选参数组合等正向边界。
* **【P2】反向场景**：包括所有输入参数校验失败、异常流程、边界值失效等反向 Case。

## 3. 校验内容与精准断言规则（核心硬性约束）
**【绝对禁止】** 出现任何形如“字段完整”、“响应成功”、“返回正确”的模糊校验。所有断言必须是具体、可量化、可代码化的。

请严格分类并遵循以下 10 条优化规则进行“预期结果”的断言设计：

### A. 基础与结构校验
1. **彻底拒绝模糊性**：必须将模糊描述替换为明确断言。例如：禁止写“响应成功”，必须写“HTTP 状态码为 200 且响应体中的 code 为 0”。
2. **结构与字段名**：校验 JSON/XML 的层级结构及字段名称是否存在。**注意：不用添加“响应体为合法的 JSON 格式”这类废话。**
3. **严禁无关字段**：断言中绝对不得引入文档中未明确定义的字段（如自作聪明地添加 `created_at`、`update_time` 等）。
4. **移除顺序依赖**：针对列表/数组结构，只校验元素和枚举值在支持的范围内，**不进行任何顺序性校验**。

### B. 核心数据与业务逻辑（入参联动规则）
5. **精准入参回显校验（强约束）**：断言必须与该 Case 的输入参数达成动态精准匹配。
   * *示例 1*：若创建时传入 `format_type = 2`，则校验必须为 `format_type == 2`（绝不能写成模糊的 `format_type ∈ {0,2}`）。
   * *示例 2*：若创建时传入 `name = "Test_100"`，则校验必须为 `name == "Test_100"`（绝不能写成模糊的 `name非空且长度≤100`）。
6. **请求参数一致性**：若需要校验响应与请求参数一致（如 name/description），必须在预期结果中明确写出：`name == "请求中输入的真实值"`。
7. **核心数据类**：订单号、用户 ID、金额等业务关键字段必须精准匹配预期，支持精确匹配或明确的区间匹配。
8. **业务逻辑类**：符合业务规则。例如：创建成功返回“成功”标识及实体 ID；查询不存在的数据时，响应体应返回空集合 `[]`。

### C. 异常场景特例
9. **异常场景极简断言**：对于 P2 异常/反向场景，**只需要给出错误码（如 code != 0 或特定的 errorCode）**，不需要给出任何其他冗余的字段校验。

### D. 类型与边界校验
10. **类型与合规性**：必填校验需明确标出字段名和非空检查（如 `NotNull`）；类型校验需明确字段名和具体类型；枚举值校验需明确字段名和合法的取值范围。
