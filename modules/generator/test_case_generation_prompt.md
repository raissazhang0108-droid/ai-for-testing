## 执行步骤（必须严格按顺序流转，禁止跳过或合并步骤）

### Step 0 — 确定执行模式与基线
在开始前，必须通过首句明确声明本次执行模式：
* **模式 A（有待测分支）**：【代码增量优先】模式。以代码改动（Diff）为核心骨架，PRD 作为业务对照。后续 Step 2、3 必须深度执行，且在最终飞书文档中必须保留独立的“代码与 PRD 实现差异”章节。
* **模式 B（无待测分支）**：【PRD 需求优先】模式。跳过 Step 2，改为基于仓库链接（使用代码搜索/语义检索工具）进行整体探索，补充已有上下文，Step 3 转化为“PRD ↔ 现有代码能力映射”。

### Step 1 — 深度读取与拆解 PRD
* **工具调用**：若 PRD 是飞书链接，优先调用 `mcp__Lark__GetDocument` 等对应工具拉取全文；若是本地文本，直接读取。
* **输出结构化摘要**：
  * **业务目标**：该需求解决什么痛点。
  * **核心链路**：正向 happy path 序列。
  * **关键字段状态机**：重点提取枚举值、状态流转触发条件。
  * **边界与异常分支**：PRD 中明确提及的失败捕获。
  * **拓扑依赖**：该微服务上下游的强弱依赖关系。

### Step 2 — 静态代码 Diff 审计（仅模式 A 执行）
对分支进行增量扫描，不得只看单行，需结合上下文文件（重点关注：`biz/handlers/`、`biz/services/`、`dal/`、`idl/`）。
* **输出改动透视图（严格按下表格式输出）**：

| 文件路径:行号 | 变更类型(新增/修改/删除) | 核心业务逻辑描述 | 影响的微服务接口/DB表 | 潜在隐藏风险点评估 |
| :--- | :--- | :--- | :--- | :--- |
* **对齐法则**：
  - 代码实现 且 与 PRD 一致 ➔ 正常用例
  - 代码已实现 但 PRD 未提及 ➔ 标记为 `【代码扩展项】`
  - 代码未实现 但 PRD 有要求 ➔ 标记为 `【PRD 缺口】`
  - 代码与 PRD 行为存在冲突 ➔ 标记为 `【实现差异】`（必须记录字段、入参、出参、报错码的具体不同）

### Step 3 — 建立 PRD ↔ 代码 双向映射矩阵
* **模式 A**：将 PRD 的每个需求点/Feature 细颗粒度映射到具体改动的 `file:line`。
* **模式 B**：将 PRD 的需求点映射到仓库中已有的存量模块/接口，评估复用度与改动成本。
* **状态打标规则（强校验）**：
  - ✅ **一致**：PRD 有要求且代码已一致实现
  - ⚠️ **缺口**：PRD 有要求但代码未覆盖（需提 Issue）
  - ❓ **扩展**：代码有改动但 PRD 未描述（需与 PM 对齐）
  - ❌ **冲突**：代码与 PRD 行为不一致（**实现差异，必须在文档单设章节重点高亮**）

### Step 4 — 矩阵化用例设计（深度下钻）
遵循“**单条用例单断言**”原则，拒绝“一例多测”。必须 100% 覆盖以下 8 大维度：
1. **功能正向用例**：主业务流流转、多接口串联、全链路 Happy Path。
2. **参数与边界值**：字段非空/必填校验、字符串长度极限、整型数值溢出、非合法枚举值、时区与时间格式边界。
3. **微服务业务异常**：库存/余额等临界值不足、活动状态机非法幂等迁移、并发竞态（如抢占锁）、防重放与幂等请求。
4. **分布式一致性**：DB 写入、Redis 缓存（剔除/穿透/更新）、MQ 消息发送（RocketMQ/Kafka）的三方最终一致性，以及底层事务回滚。
5. **多租户与数据安全**：横向越权、纵向越权、多租户数据隔离性验证、未授权（无 Token）阻断。
6. **新老兼容性与灰度**：线上存量老数据/老配置在新逻辑下的表现、TCC 灰度开关（On/Off）双向行为比对。
7. **稳定性与容灾**：下游 Kitex RPC 超时/熔断/降级表现、慢查询边界、高并发流量下的预期排队。
8. **影响面回归**：基于改动文件被引用的全局搜索（Grep/Go 调用链分析），精准锁定受影响的存量旧链路。

2. **用例明细表（按模块分组，使用 Markdown 格式）**：

| 用例 ID | 所属模块 | 优先级(P0-P3) | 前置条件 | 操作步骤 | 测试数据 | 预期结果(含断言点) | 关联 PRD 条目 | 关联代码位置 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

### Step 5 — 异步渲染并写入飞书文档
调用 `lark-doc` 等空间创建 API，在企业指定云空间创建文档：
* **文档标题规范**：`【测试用例】{{需求名}} - {{执行模式(A/B)}} - {{YYYYMMDD}}`
* **文档标准骨架（一级标题）**：
  1. 需求概述与上下文
  2. 执行模式说明（注明 A/B 模式及基线）
  3. 代码改动清单表格（仅模式 A 提供）
  4. PRD-代码映射矩阵
  5. **代码与 PRD 实现差异及冲突项**（若存在 ❌ 项，必须逐条列出：差异点 / 代码实际行为 / PRD 预期 / 建议解决方案）
  6. 测试用例总览与明细
     - 6.1 全量用例脑图（直接嵌入 Mermaid 或画板 Block）
     - 6.2 用例明细（支持按模块拆分成多张飞书原生表格 Block）
  7. 风险、技术债与遗留问题
  8. 附录：Git 命令执行记录 / 关键核心 Diff 代码片段

# Constraints & Rules
1. **真实可追溯**：严禁无中生有。所有测试点、前置条件必须能追溯到 PRD 的具体段落或代码的 `file:line`。
2. **冲突暴露**：若发现代码逻辑和 PRD 矛盾，AI 严禁自行调和或猜测，必须在矩阵中以 ❌ 暴露出来，由人工决策。
3. **拒绝本地残留**：不要在 Agent 运行的本地磁盘创建 `.md` 等临时文件，所有结果最终通过飞书 API 一站式交付。
4. **原子化汇报**：现在，请严格按照 Step 1 ➜ Step 5 的顺序执行。**每完成一个大步骤，必须用一句话简要向我汇报当前进度与核心发现，得到我确认后再进行下一步。**
